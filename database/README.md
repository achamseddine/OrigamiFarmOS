## Baseline rule
Database Baseline v1 is the consolidated starting point for executable development. Do not infer a different physical schema merely because a conceptual entity exists in the ontology. Schema changes require reviewed migrations, tests and documentation updates. Projections are non-authoritative; posted ledgers/history are immutable.

## Feed Performance Intelligence
Read `FEED-PERFORMANCE-INTELLIGENCE.md` after Feed, Procurement, Production and Health schemas. It defines analytical projections/assessments over canonical supplier-lot → batch → feeding → production lineage. These tables never become a shadow feed, inventory, production or health ledger.

## The executable schema
- `migrations/` (Alembic, run from `backend/alembic.ini`) is how a database gets its schema: `cd backend && alembic -c alembic.ini upgrade head`. Every migration carries its downgrade.
- `schema.sql` is the same schema rendered as PostgreSQL DDL from the ORM metadata — a generated file (`cd backend && python -m app.export_schema`), for reading, review and provisioning a database by hand (then `alembic stamp head`). It is not edited directly; `backend/tests/test_generated_artifacts.py` fails when it is stale.
- `backend/tests/test_migrations.py` proves the two agree table by table, column by column, index by index — on SQLite in every run and on PostgreSQL 16 in CI — and that the demo seed applies to the migrated schema.
- `seed_demo_data.sql` is the portable SQL seed of the original MVP tables; `python -m app.seed` (demo farm) and `python -m app.seed_production` (real accounts) are the maintained seeders.

### Documented physical deviations from the design documents
- Reference tables are keyed by their codes (`species.code`, `management_profiles.code`, `capabilities.code`, `units_of_measure.code`), not by a surrogate `uuid`; the codes are the values every API payload and the tablet's cache already carry. See `architecture/ADR-002-REFERENCE-KEYS-UOM-SCHEDULER-GENERATED-ARTIFACTS.md`.
- Identifiers are 36-character strings generated by the application (UUIDs; readable ids in demo data), timestamps are `TIMESTAMP WITH TIME ZONE` in UTC, JSON columns are plain `JSON` — the types the models declare and the migrations create on PostgreSQL.
