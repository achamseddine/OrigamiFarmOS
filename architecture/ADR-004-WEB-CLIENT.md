# ADR-004 — The web version is the tablet app compiled for the browser

**Status:** Accepted (v0.7.5)

## Context
The farm asked for a web version of the app "with all the features, same look and feel", against the same API and database. The tablet app (`mobile/flutter_app`) is Flutter, which compiles to the web from the same code. `CLAUDE.md` describes the web application as "management/administration oriented" and `pnpm-workspace.yaml` lists an empty `web` package from the original TypeScript plan (ADR-001); neither has been built.

## Decision
The web version is **the same Flutter app**, built with `flutter build web`, not a second application.

- **One codebase, one set of screens and rules.** Every module, form, permission check, the Arabic/RTL layout and the duplicate and approval behaviour are the tablet's, unchanged. What a person sees is decided by their module permissions exactly as on the tablet — the web build is not limited to management screens; the farm decides who gets which module.
- **Offline store in the browser:** `sqflite_common_ffi_web` (new dependency) runs the same SQLite schema as WebAssembly in a shared worker, persisted in the browser's IndexedDB. The cache, the outbox with its idempotency keys, and the bundled demo farm (`ali` / `ali123`) work in the browser as on the tablet; storage is per browser and per site address. `web/sqlite3.wasm` and `web/sqflite_sw.js` are generated by `dart run sqflite_common_ffi_web:setup` and committed.
- **Hosting:**
  1. *The farm server* serves the built app at `/app/` (`backend/app/web_client.py`), from `FARMOS_WEB_DIR` or `backend/web_app/`. Same address as the API: no server address to type, no cross-origin setup. `index.html` is served with its base rewritten to `/app/`; WebAssembly is served as `application/wasm`; files whose names do not change between builds are revalidated on every load.
  2. *GitHub Pages*, from `.github/workflows/build-web.yml` on the main tablet branch only (one site, one source), for opening the app from a link — the demo farm, or the tablet's default server, another one set on the sign-in screen, or the `FARM_API_URL` repository variable. The API already allows any origin (`CORSMiddleware`, bearer tokens, no cookies).
- **Server address:** opened from a farm server's `/app/`, that server (`<origin>/api/v1`, `startupApiBaseUrl()`); otherwise the tablet's default (`kDefaultApiBaseUrl`, `FARMOS_API_BASE_URL` at build time); the sign-in screen can change it on both.
- **Built together:** every app change builds the APK and the web app from the same commit (`build-apk.yml`, `build-web.yml`, same triggers); both sign-in screens show that commit. `scripts/verify-all.sh` runs before every commit.
- **Self-contained graphics engine:** builds use `--no-web-resources-cdn`, so CanvasKit is served with the app instead of from Google's CDN.

## Consequences
- A feature built once appears on the tablet and on the web; the layout sweep (`test/layout/tablet_sizes_test.dart`) covers both.
- Device features differ by platform: the camera QR scan needs HTTPS (or localhost) and the browser's camera permission; label sheets print through the browser's print dialog; there is no file-system photo path in a browser (an uploaded photo is a URL).
- The web build is ~47 MB uncompressed (the graphics engine variants and the app's artwork); the first load fetches what the browser needs (~10 MB), later loads revalidate.
- The empty TypeScript `web` package of ADR-001 is superseded for the client; ADR-001's backend choices are out of scope here.
